- **[high, VERIFIED LOCALLY]** Compatibility is strictly one-directional and version-stamp gated: newer KiCad reads all older formats (10.0 read every 7.0 file tested), but older kicad-cli refuses newer files (7.0/8.0 exit 127 with 'created with a more recent version ... upgrade KiCad to version 10.0 or later (file format dated 20260206 or later)'; 9.0 exit 3 'Failed to load board/schematic'). Parsers are strict: appending a single unknown token `(embedded_fonts no)` to a 7.0 file makes 7.0 and 8.0 fail ('Unknown token ...', exit 127 for pcb, exit 3 for sch) while 9/10 accept it; a 7.0-content board whose header claims a future version (20990101) is rejected by 10.0 (exit 3); conversely 10.0 accepts a 10-content file whose header lies '20230121'. Therefore the wrapper's serializer must emit an exactly version-conformant token set AND the matching version stamp for the target install; there is no 'lowest common denominator' file that all four read except one written in the oldest target's format.
  - Evidence: fwd/ and tol/ experiments: kicad-cli 7.0/8.0/9.0 `pcb export pos` / `sch export netlist` on 10.0-written files; 7.0 on 8.0 board; 8.0 on 9.0 board; tol/sch7_plus_token.kicad_sch, tol/pcb7_plus_token.kicad_pcb, tol/pcb_future.kicad_pcb, tol/sch10_claims7.kicad_sch with exit codes captured.

- **[high, VERIFIED LOCALLY]** The IPC server is OFF by default and gated by kicad_common.json 'api.enable_server' (user's 9.0 and 10.0 configs both have false). A wrapper can enable it without touching user settings by launching the GUI with its own KICAD_CONFIG_HOME containing <major.minor>/kicad_common.json {"api":{"enable_server":true}}. On KiCad 10 an isolated config additionally triggers the modal 'KiCad Setup' STARTWIZARD (which blocks the API with 'KiCad is not ready to reply') unless ALL of these hold: kicad_common.json exists (settings provider), do_not_show_again.update_check_prompt AND data_collection_prompt are true (privacy provider), and the global sym-lib-table, fp-lib-table AND design-block-lib-table files exist (LIBRARY_MANAGER::GlobalTablesValid, libraries provider). ## Capabilities

- A single wrapper can drive 7.0.6, 8.0.1, 9.0.5 and 10.0.0 today from installed binaries only: file-level IR + per-target serializer, kicad-cli for ERC/DRC/exports (8+; 7 only exports), each install's bundled python.exe for SWIG board scripting (place/move footprints, ZONE_FILLER, WriteDRCReport, SaveBoard), and kipy IPC against a GUI instance for 9/10 (live edits, commits, refill zones, RunAction).
- Deterministic install discovery on Windows: registry Uninstall keys (DisplayName 'KiCad X.Y', InstallLocation) + Program Files glob, then `kicad-cli version --format plain|commit` for exact version; config isolation via KICAD_CONFIG_HOME (auto <major.minor>/ subfolder), stock-data override via KICAD_STOCK_DATA_HOME, project-relative libs via ${KIPRJMOD}.
- Format migration is a one-liner per file with 10.0 (`kicad-cli sch upgrade`, `pcb upgrade`, `sym upgrade`, `fp upgrade`) and per-version SWIG LoadBoard/SaveBoard for boards on 7-10; upgrade is lossless-forward and always in place (copy first).
- Env-var portability is largely solved by KiCad itself: any KICAD<N>_SYMBOL_DIR / _FOOTPRINT_DIR / _3DMODEL_DIR reference resolves under 8+ (3D under 7+), so the wrapper can write lib tables with the CURRENT major's variable and old projects keep working on newer installs.
- Version-agnostic error handling: kicad-cli exit codes 0-6 are stable; ERC/DRC JSON ($schema erc.v1/drc.v1) has been additive-only from 8 to 10; kipy surfaces unsupported RPCs as ApiError 'no handler available for request of type ...' giving runtime capability probing; `kicad-cli <cmd> --help` output is a reliable feature probe if exit status is ignored.
- One IPC client library (kipy 0.8.0) talks to both 9.x and 10.x servers; KiCad.get_version()/get_api_version() plus try/except per RPC yields a live capability map without pinning kipy per major.
- GUI-side plugin channel is possible without any source build: 7/8 via SWIG Action Plugins (Documents/KiCad/<ver>/scripting/plugins), 9/10 via IPC plugins (plugin.json, runtime 'exec' or 'python', KICAD_API_SOCKET/TOKEN injected) or simply an external kipy client connecting to api.sock; the VS Code extension can own the socket path by launching the GUI with an isolated KICAD_CONFIG_HOME where api.enable_server=true.

## Limitations

- No forward compatibility at all: a file written by version N cannot be opened by N-1 (hard error, exit 3/127), and even a single unknown token or a future version stamp is fatal on older parsers. The wrapper must serialize per target version (exact token set + exact (version N) stamp) or always target the oldest install the user wants to keep opening the project with.
- 10.0 changed board semantics, not just syntax: netcodes are gone (nets by name), layer IDs were renumbered in 9, layerselection bitmask width changed, footprint child order changed - so a naive text/regex diff or patch approach across majors is unsafe; the IR must be semantic (nets by name, layers by name).
- KiCad 10 ships no .wrl models; STEP/GLB exports of 7/8/9-era boards referencing *.wrl silently drop those models unless the wrapper rewrites references to .step (the --subst-models flag does not rescue a missing .wrl).
- IPC API in 9 and 10 is GUI-only (no headless, no plotting) and PCB-only (zero schematic commands even in kipy 0.8.0); headless kicad-cli IPC and export RPCs only arrive with KiCad 11 - so schematic authoring must be file-level in every currently installed version.
- SWIG pcbnew is deprecated (warning on import in 9 and 10, removal planned), ABI-locked to each install's bundled Python (3.9 for 7, 3.11 for 8/9/10) and its own DLL dir; it cannot be imported into the VS Code extension's Python; each version needs its own subprocess driver and API names drift (IO_MGR -> PCB_IO_MGR).
- kicad-cli 7.0 has no ERC/DRC/BOM at all (only exports); ERC/DRC via CLI starts at 8.0. For 7 the only DRC path is SWIG WriteDRCReport in 7's python.
- Headless runs still need a config dir: kicad-cli silently creates <KICAD_CONFIG_HOME>/<ver>/ json files but not lib tables; without global tables ERC emits lib_symbol_issues/footprint_link_issues and library-backed operations fail. The wrapper must provision {sym,fp,design-block}-lib-table from share/kicad/template into its own config root per version (and, for GUI/IPC on 10, satisfy the STARTWIZARD conditions).
- kicad-cli 10.0 writes a .kicad_prl side file into the project dir on read-only operations; 7/8 do not create output directories for gerbers; --help exits 1 on 7/8 - all need normalisation in the wrapper.
- Registry discovery is inconsistent (7 under WOW6432Node with uninstaller.exe; 8-10 under the 64-bit hive) and there is no HKLM\SOFTWARE\KiCad key; portable/zip installs and Linux/macOS need path-based discovery.
- Some observations are for the exact installed builds (7.0.6, 8.0.1, 9.0.5, 10.0.0); later point releases (e.g. 10.0.1 adds IPC handlers, 9.0.8 adds layer-name RPCs) shift the capability map within a major, so capability flags must key on full semver, not major.
- GUI-based IPC tests are fragile in shared environments: a sibling task's `taskkill /IM pcbnew.exe` killed this task's instance mid-test; only one GUI instance per default api.sock is safe unless KICAD_API_SOCKET is set per instance.

## Recommendations

- Adopt a 'KiCadInstallation' abstraction: {root, bin/kicad-cli.exe, bin/python.exe (+site-packages, DLL dir), share/kicad/{symbols,footprints,3dmodels,template,schemas}, semver from `kicad-cli version --format plain`, commit hash, python ABI tag}. Discover via registry Uninstall scan + Program Files glob + PATH + explicit setting; cache per root. Derive a capability record keyed on FULL semver (not major): cli_subcommands (probe `--help`, ignore exit code), cli_flags per subcommand (parse help), has_erc_cli (>=8), has_drc_cli (>=8), has_jobset (>=9), has_upgrade_cmds (>=10), has_ipc (>=9), ipc_headless (>=11), ipc_schematic (none through 10), swig_available (all; deprecated >=9), gerbers_creates_dir (>=9), writes_prl_side_file (>=10), ships_wrl (<=9), legacy_var_fallback {3d>=7, sym/fp>=8, 3rdparty>=9}. Ship the verified matrix (scratchpad kicad_version_matrix.json) as seed data and re-probe at runtime.
- Own a canonical semantic IR for schematic, symbol, board and project (nets by name, layers by canonical name, UUIDs, properties as maps, units in nm/mm, booleans as booleans) and implement one serializer per supported format epoch: sch {20230121, 20231120, 20250114, 20260306}, pcb/mod {20221018, 20240108, 20241229, 20260206}, sym {20220914, 20231120, 20241209, 20251024}, pro meta {1, 3}. Each serializer emits EXACTLY that epoch's token set and version stamp (no extra tokens, correct hide/yes-no/tstamp forms, correct layer-ID table and layerselection width, numeric net table for <10 and name-only nets for 10). Default the project's target epoch to the oldest KiCad the user wants to open it with, and expose 'upgrade project to <install>' using kicad-cli 10 sch/pcb/sym/fp upgrade (copy first, then diff) or SWIG LoadBoard/SaveBoard for 7-9 boards.
- Read with a real s-expression parser that tolerates every epoch (both bare `hide` and `(hide yes)`, tstamp and uuid, fp_text and property, numeric or named nets, both layer-ID tables) and normalises into the IR; never regex/line-parse files, netlists or reports (10.0 reformatted netlists to one token per line).
- Backend routing per operation: schematic create/edit/annotate -> IR + serializer (file level) on every version (no schematic API exists through 10); ERC/DRC/BOM/netlist/fab outputs -> kicad-cli (8+; on 7 use exports only and SWIG WriteDRCReport for DRC); board generation/placement/zone fill/save headless -> SWIG driver subprocess `<install>/bin/python.exe driver.py` with a per-major shim (IO_MGR vs PCB_IO_MGR), or kipy IPC when a GUI session is open (9/10); routing -> external (Freerouting DSN/SES round-trip via IR) plus IPC/SWIG track creation, until KiCad exposes a router RPC. Encode the per-version choice in the capability record so upgrading KiCad only adds/changes flags.
- Run every KiCad process with a wrapper-owned environment: KICAD_CONFIG_HOME=<ext-storage>/kicad-config (KiCad appends <major.minor>/), pre-provisioned per version with kicad_common.json {api.enable_server:true, do_not_show_again.update_check_prompt:true, data_collection_prompt:true, ...} and copies of share/kicad/template/{sym,fp}-lib-table plus an empty `(design_block_lib_table (version 7))` for 9/10, so kicad-cli, SWIG and GUI/IPC all see identical libraries and 10's setup wizard never appears; never touch %APPDATA%\kicad. Always mkdir output dirs, tolerate/ignore the .kicad_prl side file on 10 (add to .gitignore), and pass KICAD_API_SOCKET per GUI instance if more than one may run.
- Write lib tables using the target install's own variable (KICAD<major>_SYMBOL_DIR etc.) but rely on KiCad's legacy fallback so projects survive KiCad upgrades; still rewrite `${KICAD<N>_...}` to the current N when the wrapper upgrades a project, and rewrite *.wrl model refs to *.step when targeting 10+. For 3rd-party/project libs prefer ${KIPRJMOD}-relative tables.
- Treat kipy as 'latest that supports all installed majors' (0.8.0 covers 9 and 10) and probe RPCs at runtime (catch 'no handler available'); log KiCad.get_version()/get_api_version() and gate features by full semver. Do not pin kipy per major. Plan for KiCad 11 by making the IPC backend also usable headlessly (docs say kicad-cli will host the API and expose plotting), at which point IPC can replace SWIG entirely.
- In-KiCad plugin <-> VS Code channel: do NOT build a C++ plugin or require a source build. For 9/10 the VS Code extension should itself be the IPC client (kipy or a TypeScript nng+protobuf client) connecting to api.sock; register an optional IPC plugin.json (runtime 'exec') only to add a toolbar action that pokes the extension (KiCad passes KICAD_API_SOCKET/TOKEN). For 7/8 an optional SWIG Action Plugin in Documents/KiCad/<ver>/scripting/plugins can expose a small localhost RPC (stdlib socket/json) into the running pcbnew for live edits; both plugin types are Python and version-scoped by directory. Reserve a KiCad source build strictly for debugging KiCad-side behaviour (KICAD_RUN_FROM_BUILD_DIR is supported) or for prototyping RPCs to upstream - anything patched into KiCad C++ becomes a per-version fork and breaks the 'upgrade KiCad underneath' goal.
- Add a regression corpus to the wrapper's CI: the four demo/template projects here, run `read -> IR -> serialize(epoch) -> kicad-cli <that version> netlist/drc/erc` for each installed version, and diff IR round-trips; include the tol/ style negative tests (unknown token, future stamp) so a serializer regression is caught before users hit 'created with a more recent version'.
