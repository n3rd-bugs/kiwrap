# vscode-agent-surface: exposing one KiCad tool backend to Claude Code, Copilot agent mode, Cursor, Windsurf and Codex from a VS Code extension (MCP, VS Code LM Tools API, extension UI surfaces, Agent Skills)

## Findings

- **[high, VERIFIED LOCALLY]** The current MCP specification revision is 2026-07-28 (previous: 2025-11-25). It makes the protocol stateless: the initialize/notifications/initialized handshake and Mcp-Session-Id are removed, every request carries protocolVersion/clientInfo/clientCapabilities in _meta, a new server/discover RPC is mandatory for servers, all results carry a required resultType ('complete' | 'input_required'), server-initiated requests (roots/list, sampling/createMessage, elicitation/create) are replaced by the Multi Round-Trip Request pattern, tools/list results must carry ttlMs and cacheScope, and Roots, Sampling and Logging features are Deprecated (12-month removal window). HTTP+SSE transport is Deprecated; stdio and Streamable HTTP remain.
  - Evidence: Changelog page lists these as Major changes 1-9, Minor 5, Deprecated 1-2. Locally, mcp 2.2.0 exposes mcp.types.LATEST_PROTOCOL_VERSION == '2026-07-28' and my Client negotiated protocol_version 2026-07-28 with tools/list returning resultType='complete', ttlMs=0, cacheScope='private'.
  - Sources: https://modelcontextprotocol.io/specification/2026-07-28/changelog, https://blog.modelcontextprotocol.io/posts/2026-07-28/, https://modelcontextprotocol.io/specification/2026-07-28/server/tools
- **[high]** Design consequence of 2026-07-28: do NOT build the KiCad wrapper on Roots, Sampling, Logging notifications or per-connection state. State that must persist across calls (e.g. an open board / live KiCad session handle) must be an explicit server-minted handle returned by a creation tool and passed as an ordinary argument; logging should go to stderr (stdio) or OpenTelemetry.
  - Evidence: Spec 'Stateful Tools' section (non-normative) and Deprecated section: 'pass directories or files via tool parameters ... instead of Roots; ... log to stderr (stdio) or use OpenTelemetry instead of Logging'.
  - Sources: https://modelcontextprotocol.io/specification/2026-07-28/server/tools, https://modelcontextprotocol.io/specification/2026-07-28/changelog
- **[high, VERIFIED LOCALLY]** MCP tool results can contain images: content items of {type:'image', data:<base64>, mimeType:'image/png'} alongside text, audio, resource_link, embedded resource and structuredContent (validated by an optional outputSchema); isError:true carries model-recoverable errors. The spec states no byte-size limit for image data; limits are client-side.
  - Evidence: Ran a Python MCP stdio server whose tool executes `kicad-cli pcb render` on the ecc83 demo board and returns Image(path=...); the client received ImageContent mime=image/png, base64_len=66100, decoded 49,574 bytes with PNG magic; wrote it back to roundtrip.png and visually confirmed it is the rendered 3D board. run_drc returned structuredContent (keys exit_code/violations/unconnected_items/report) and export_pcb_svg returned a resource_link file:// URI.
  - Sources: https://modelcontextprotocol.io/specification/2026-07-28/server/tools
- **[high, VERIFIED LOCALLY]** Python SDK: PyPI package `mcp` is at 2.2.0 (requires Python >=3.10); v2 renamed FastMCP to MCPServer (`from mcp.server import MCPServer`; `mcp.server.fastmcp` no longer exists and raises a migration hint), transport is chosen at run time (`mcp.run(transport='stdio'|'sse'|'streamable-http')`, `run_stdio_async()`, `run_streamable_http_async(host, port, streamable_http_path='/mcp', stateless_http=False, ...)`, `streamable_http_app()` for ASGI), image helper is `from mcp.server.mcpserver import Image` (Image(path=|data=, format=)), tool decorator is `@mcp.tool(name, title, description, annotations: ToolAnnotations(read_only_hint, destructive_hint, idempotent_hint, open_world_hint), icons, meta, structured_output)`. `structured_output=True` requires a typed return (plain `dict` raises InvalidSignature; `dict[str, Any]` works). Client side: `from mcp.client import Client; async with Client(StdioServerParameters(...)|'http://host/mcp') as c: c.list_tools()/call_tool()`; Client.mode='auto' probes server/discover and falls back to legacy initialize. The unofficial `fastmcp` package (jlowin) is separately at 4.0.5.
  - Evidence: uv venv + `uv pip install mcp[cli]` installed mcp 2.2.0; introspected signatures with inspect; first run failed with `InvalidSignature: Function run_drc: return type <class 'dict'> is not serializable for structured output`, fixed with dict[str, Any]; PyPI JSON confirms versions.
  - Sources: https://py.sdk.modelcontextprotocol.io/v2/whats-new/, https://pypi.org/pypi/mcp/json, https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/
- **[high, VERIFIED LOCALLY]** An mcp 2.x server transparently serves legacy clients: a raw JSON-RPC `initialize` with protocolVersion 2025-06-18 was accepted, returned the old-style capabilities object, tools/list and tools/call worked with the legacy wire shape (no resultType/ttlMs), so agents that have not yet adopted 2026-07-28 (older VS Code/Cursor/Codex builds) keep working. After a legacy initialize, server/discover on that session returns -32601 Method not found (expected).
  - Evidence: legacy_probe.py output: initialize -> {protocolVersion: '2025-06-18', serverInfo: {name: 'kicad-probe'}...}; tools/call kicad_version -> '9.0.5' with structuredContent {result: '9.0.5'}.
  - Sources: https://py.sdk.modelcontextprotocol.io/v2/whats-new/
- **[high, VERIFIED LOCALLY]** Streamable HTTP also works with the same server object: `mcp.run(transport='streamable-http', host='127.0.0.1', port=8765)` served /mcp; the v2 Client over HTTP negotiated 2026-07-28 and called tools against KiCad 7.0.6 and 8.0.1 kicad-cli. - **[high]** Agent Skills (SKILL.md) is an open standard (agentskills.io, published by Anthropic Dec 2025) adopted by Claude Code, Codex CLI, GitHub Copilot (VS Code, CLI, cloud), Cursor, Windsurf, Gemini CLI. ## Capabilities

- One Python MCP stdio server (mcp>=2.2, MCPServer) can be registered unchanged in Claude Code (.mcp.json / claude mcp add), VS Code Copilot (.vscode/mcp.json, user mcp.json, code --add-mcp, or programmatically via vscode.lm.registerMcpServerDefinitionProvider), VS Code Agent Host Copilot/Claude/Codex harnesses (reads workspace .mcp.json natively), Cursor (.cursor/mcp.json), Windsurf (mcp_config.json), Codex (config.toml) and Copilot CLI (mcp-config.json).
- Tools can return PNG images (ImageContent base64) so vision-capable agents inspect rendered boards/schematics - verified end-to-end with kicad-cli pcb render (board) and kicad-cli sch export pdf + PyMuPDF (schematic); structuredContent + outputSchema give machine-readable ERC/DRC reports; resource_link can hand back large artifacts (SVG, Gerber zips) by URI.
- The server negotiates both the new stateless 2026-07-28 protocol and legacy 2025-xx clients automatically (verified), so all current agent builds work.
- Streamable HTTP is available from the same server object (verified) for remote/agent-host scenarios; stdio for local.
- A VS Code extension can (a) auto-register the same server for Copilot users with zero config, (b) add a Copilot-only LM-tool facade with confirmation UI, #-references and LanguageModelDataPart.image, (c) show .kicad_sch/.kicad_pcb previews via a read-only custom editor + webview fed by kicad-cli SVG, (d) push ERC/DRC results into the Problems panel via DiagnosticCollection, (e) expose jobs as Tasks and a tree view, (f) write .mcp.json / .cursor/mcp.json / config.toml for other agents on demand.
- A single .claude/skills/kicad-flow/SKILL.md (Agent Skills standard) teaches the workflow to Claude Code, Copilot (VS Code/CLI), Codex, Cursor and Windsurf; AGENTS.md/CLAUDE.md/.github/copilot-instructions.md add always-on guidance.
- VS Code MCP dev mode (dev.watch + dev.debug type python) lets you set breakpoints in the Python MCP server while an agent drives it; Claude Code's `claude mcp get/list` health-checks the same server from the terminal.
- VS Code's bundled Node (v24.18.1) can execute JS via ELECTRON_RUN_AS_NODE, useful for running a TS MCP server without a system Node, but not for npm-based development.

## Limitations

- VS Code Language Model Tools (vscode.lm.registerTool) are consumed only by VS Code's own chat (Copilot Local harness; forwarded to Agent Host sessions only while that window is connected). Claude Code (CLI and extension), Cursor's agent, Windsurf and Codex never see them - so they can only be a thin optional facade, never the primary surface.
- Cursor does not implement vscode.lm.registerMcpServerDefinitionProvider (open forum request), and the Claude Code extension does not read VS Code mcp.json; therefore programmatic registration reaches Copilot only. For the others the extension must write their config files (.mcp.json, .cursor/mcp.json, ~/.codex/config.toml, ~/.codeium/windsurf/mcp_config.json) or the user runs `claude mcp add` / `codex mcp add`.
- Config key mismatch: VS Code uses `servers`, everybody else `mcpServers`; Copilot CLI uses type 'local' and requires a `tools` allowlist; Codex uses TOML `[mcp_servers.x]` with a 10 s startup timeout and 60 s tool timeout by default (long DRC/route/export jobs must raise tool_timeout_sec or run asynchronously and poll).
- Tool-count caps: Cursor 40 (silently truncates), Windsurf 100, VS Code 128 per request. Keep the KiCad tool set compact (~20-35 tools) and prefer enum-parameterised tools over one tool per subcommand.
- Image results count against Claude Code's MAX_MCP_OUTPUT_TOKENS (default 25k, no file spill for images); keep renders <= ~1024 px / < 100 KB or raise the limit. Codex image support is undocumented.
- Claude Code project-scope .mcp.json servers start 'Pending approval'; team auto-approval needs enableAllProjectMcpServers (only the user-level settings file affected the non-interactive `claude mcp list` health check in my test).
- The Claude Code VS Code extension only reliably reads project .mcp.json (an April-2026 issue about ~/.claude.json user scope was closed 'not planned'); its slash-command/skill subset is smaller than the CLI's.
- The 2026-07-28 spec deprecates Roots, Sampling and Logging and removes per-connection state: a wrapper must not rely on the client telling it the workspace root (pass paths as tool args) nor on server-side session state (return explicit handles).
- No node/npm on this machine: the TS extension shell cannot be built or vsce-packaged here until Node LTS is installed; the skeleton I wrote was API-checked against vscode.d.ts 1.138 but not compiled.
- KiCanvas is early alpha with an unstable embedding API and no documented KiCad 9/10 support; kicad-cli SVG/PDF output is the dependable preview source.
- MCP Apps (interactive UI in chat) work in VS Code and Cursor only; Claude Code CLI has no rendering surface for them.
- kicad-cli 7.0 lacks drc/erc/render entirely, so on KiCad 7 those tools must fall back to pcbnew SWIG scripting or report 'unsupported on this version'.

## Version notes

The agent-facing surface (MCP tools + skills) is KiCad-version-independent; version differences live behind the server's backend adapter. Verified locally: kicad-cli 7.0.6 offers only `pcb export`/`sch export` (no drc/erc/render/jobset); 8.0.1 adds `pcb drc` and `sch erc` (with --format json); 9.0.5 adds `pcb render` (PNG raytrace) and `jobset`; 10.0.0 adds `pcb import`, `pcb upgrade`, `sch upgrade`. A `major` parameter (or auto-detect from the .kicad_pro `generator_version`) on every tool let the same MCP server drive all four installs. Practical mapping: board image = `pcb render` on >= 9, else `pcb export svg/pdf` -> PNG; schematic image = `sch export pdf` + PyMuPDF on all versions; DRC/ERC via kicad-cli on >= 8, via pcbnew SWIG (bundled python.exe) on 7; the IPC API (kipy, `kicad-python` 0.8.0 on PyPI) exists only for >= 9 and is the channel for live-GUI operations - it should terminate inside the MCP server as a 'live' backend, not in the VS Code extension. MCP-side versioning: mcp 2.2.0 speaks 2026-07-28 and falls back to legacy initialize, so agent-client version skew is handled by the SDK.

## Recommendations

- Architecture 'one tool backend, many agent frontends': (1) `tools/kicad-mcp/` - a Python package (mcp>=2.2, `from mcp.server import MCPServer`) exposing ~20-35 tools (kicad_project_info, kicad_sch_*, kicad_erc, kicad_update_pcb, kicad_place, kicad_route, kicad_drc, kicad_render (Image), kicad_export{format enum}, ...) with ToolAnnotations, outputSchema/structuredContent for reports, server `instructions`, and MCP prompts for canned workflows; backends selected per KiCad major: kicad-cli, bundled pcbnew SWIG python, IPC/kipy 'live' session (>= 9), lossless file edit. Run as stdio by default, `--http` optional. (2) `.mcp.json` at repo root (Claude Code + VS Code Agent Host), `.vscode/mcp.json` (Copilot Local harness, with dev.watch/dev.debug), `.cursor/mcp.json`, and documented snippets for Codex config.toml, Windsurf, Copilot CLI (all written in scratchpad/vscode-agent-surface/configs/all-clients.md). (3) `.claude/skills/kicad-flow/SKILL.md` (spec-only frontmatter) read by Claude Code AND Copilot, plus AGENTS.md/CLAUDE.md. (4) A TypeScript VS Code extension that: registers the same server through `contributes.mcpServerDefinitionProviders` + `vscode.lm.registerMcpServerDefinitionProvider` (McpStdioServerDefinition pointing at the bundled/uv-managed Python), offers a 'Configure agents' command that writes the other clients' config files, provides a read-only custom editor preview (kicad-cli SVG in a webview), a DiagnosticCollection for ERC/DRC, a task provider, and optionally 1-3 `languageModelTools` facades (confirmation UI, #kicadRender) that call the same Python backend.
- Verdict on the 'in-KiCad plugin <-> VS Code extension' channel from the agent-surface perspective: do NOT make it the agent surface and do NOT terminate it in the VS Code extension. Any capability that only a running KiCad can provide (live GUI refresh, interactive router, selection) must be reachable from the MCP server process, otherwise terminal agents (Claude Code CLI, Codex, Copilot CLI) and Cursor lose it. If a KiCad-side plugin is needed for things the official IPC API lacks, implement it as a KiCad plugin exposing a loopback RPC (mirroring Claude Code's own `ide` server pattern: 127.0.0.1 random port + token lock file) that the MCP server's 'live' backend consumes; the VS Code extension only orchestrates (launch KiCad with KICAD_CONFIG_HOME, show status). This keeps the tool contract identical across all six agent frontends and across KiCad 7-10.
- A KiCad source build is not required for the agent surface: every experiment here used installed binaries (kicad-cli 7/8/9/10, bundled python). Reserve the source build for the sibling research on router/IPC internals (debugging why an IPC call misbehaves, or adding API methods); gate it behind a concrete failure you cannot work around from Python.
- Adopt the 2026-07-28 rules now: no Roots/Sampling/Logging dependence, explicit handles for live sessions, deterministic tools/list order, tool names 1-128 chars [A-Za-z0-9_.-], `isError:true` with actionable text for agent self-correction, `_meta['anthropic/maxResultSizeChars']` on large-report tools, and keep images <= ~1024 px.
- Keep the tool count under Cursor's 40 (the tightest cap) - use `format`/`action` enums and a `kicad_help(tool)` tool for deep option docs instead of many tools; consider VS Code virtual tools threshold for Copilot users with many servers.
- Install Node LTS (winget install OpenJS.NodeJS.LTS) before starting the extension shell; scaffold with `npm init @vscode` or the vscode-python-tools-extension-template, engines.vscode ^1.101.0, and package with @vscode/vsce 4.x. Bundle the Python server via uv (uv-managed venv created on first `resolveMcpServerDefinition`) rather than depending on system Python.
- Test matrix to automate: (a) mcp Python Client over stdio (done: kicad_probe_client.py), (b) raw legacy initialize probe (done: legacy_probe.py), (c) `claude mcp list` health check with CLAUDE_CONFIG_DIR isolated (done), (d) VS Code Extension Development Host with .vscode/mcp.json dev.debug once Node is installed, (e) Cursor/Codex smoke tests via their `mcp add` CLIs.
- Use MCP Apps later, optionally, for an interactive in-chat board viewer in VS Code/Cursor; keep the custom-editor webview as the universal preview.
