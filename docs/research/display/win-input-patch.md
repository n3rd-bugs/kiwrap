# Hidden-window input for KiCad on Windows: the `KICAD_INPUT_FROM_EVENTS` patch (spike b)

Hands-on spike, 2026-09-19/20, Windows 11 26200, two 3840x2160 monitors at 150 %, KiCad built from
the fork branch **`mr/display-input`** (`n3rd-bugs/kicad-fork`, base `base/6dd893f7d1` = nightly
10.99.0-4083, RelWithDebInfo `msvc-win64-release`). Prototype: `prototypes/display/winstream/`
(`run_events.py`, `winstream/inject_events.py`, `bench/make_build_env.py`). Upstream text:
[`../../upstream/drafts/display-input-mr.md`](../../upstream/drafts/display-input-mr.md). Sibling
spike (a), the multi-editor capture question, is [`win-multi.md`](win-multi.md); this report only
answers *"can a KiCad editor that is not on the user's desktop be driven purely with posted window
messages?"* (DISPLAY.md decision 5).

**Short answer: yes, with a 25-file / +534 −48 patch that is invisible while the variable is unset.**
Select, rotate, delete, undo (Ctrl+Z), drag-move, wheel zoom, middle-drag pan, double-click, the
properties dialog (click into a field, Ctrl+A, type, OK), the footprint chooser (A, type a filter,
Esc), the context menu (opens at the *reported* pointer, an item can be clicked, Esc closes) all
work with nothing but `PostMessage` while KiCad is covered by another window or **cloaked**
(`DWMWA_CLOAK`: not drawn on the desktop at all, still captured by WGC). The user's real cursor
never moved and the foreground never left the covering app during the runs. What stays broken:
tooltips (a comctl32 control that polls the real cursor), popup menus are OS windows that the
desktop still shows, a fully off-screen window gets no capture updates, and KiCad grabs the
foreground once at launch.

---

## 1. Why stock KiCad cannot be driven with posted messages (root causes, wx 3.3.2 sources)

| Symptom (winstream §2b) | Where the hardware is consulted | Consequence for a posted message |
|---|---|---|
| clicks select nothing, context menu opens at the real cursor, zoom centre wrong | `WX_VIEW_CONTROLS::onMotion` / `getMouseScreenPosition()` → `KIPLATFORM::UI::GetMousePosition()` → `wxGetMousePosition()` → `GetCursorPos`; `TOOL_MANAGER::dispatchContextMenu` and every status popup use the same call | the message's coordinates are ignored; the tool framework works on the physical cursor |
| drags end immediately / clicks lost | `TOOL_DISPATCHER::BUTTON_STATE::GetState()` → `wxGetMouseState()` → `GetAsyncKeyState(VK_LBUTTON)` | "button released" as soon as the physical button is up |
| Ctrl/Shift combos need real modifiers | wx fills `ControlDown()/ShiftDown()` from `GetKeyState()` (thread-synchronous state, only updated by hardware input the thread retrieves); KiCad's own `wxGetKeyState()` calls use `GetAsyncKeyState()` (physical) | posted `WM_KEYDOWN VK_CONTROL` changes neither |
| posted Esc ignored by dialogs | `wxEVT_CHAR_HOOK` is generated by a `WH_KEYBOARD` hook (`wxKeyboardHook`, `src/msw/window.cpp`), which the system runs for hardware input only; `wxDialogBase::OnCharHook`, `DIALOG_SHIM::OnCharHook`, the chooser's `OnChar`, `LIB_TREE` navigation all live on that event | keys still reach `wxEVT_KEY_DOWN`/`wxEVT_CHAR` (that is why hotkeys and typing worked), but nothing that listens to the hook |
| (new) hover state flickers, pointer position corrupted | `wxWindowMSW::GenerateMouseLeave()` builds `wxEVT_LEAVE_WINDOW` from `GetCursorPos()` + `GetKeyState()`, and `TrackMouseEvent(TME_LEAVE)` fires immediately because the real cursor is not in the window | every posted move is followed by a bogus LEAVE at the real cursor's coordinates |
| (new) wheel zoom moves the user's mouse | `center_on_zoom` (default **true**) → `CenterOnCursor()` → `WarpPointer()` → `SetCursorPos` | with stock KiCad + PostMessage each wheel step teleports the physical cursor into the hidden window |

## 2. The patch (branch `mr/display-input`, commit `67ceff363d`)

Gate: environment variable `KICAD_INPUT_FROM_EVENTS` (`1`, or `cloak`). Nothing changes while it is
unset; GTK/macOS get stub implementations. Diffstat: 25 files, +534 −48; the substance is
`libs/kiplatform/port/wxmsw/ui.cpp` (+365) and `kiplatform/ui.h` (+47), the rest is a mechanical
sweep of the callers that polled the hardware directly.

| Piece | What it does |
|---|---|
| `KIPLATFORM::UI::InputFromEvents()` | cached env check |
| `KIPLATFORM::UI::GetMousePosition()` | returns the screen position of the last mouse event (or last warp) instead of `GetCursorPos` |
| `KIPLATFORM::UI::GetMouseState()` (new) | buttons of the last mouse event + thread-synchronous modifier state; replaces `wxGetMouseState()` in the tool dispatcher (button state, `flushPendingClicks`), the three selection tools, the footprint/symbol/design-block choosers, the 3D preview |
| `KIPLATFORM::UI::IsKeyDown()` (new) | `GetKeyState()` instead of `GetAsyncKeyState()`; replaces `wxGetKeyState()` in `WX_VIEW_CONTROLS` (motion-pan modifier, `refreshMouse` modifiers), `TOOL_DISPATCHER` (stale auto-repeat check), `COMMON_TOOLS`, `ACTION_MENU`, the Tab view/preset switchers (`EDA_VIEW_SWITCHER`, `PCB_BASE_EDIT_FRAME`, 3D viewer), `SCH_MOVE_TOOL` |
| `KIPLATFORM::UI::WarpPointer()` | moves the reported position only, returns true (keyboard cursor moves, `CenterOnCursor` keep working logically; the physical cursor is never touched) |
| `KIPLATFORM::UI::InfiniteDragPrepareWindow()` | returns false in this mode; the drag-zoom edge warp now honours a refused warp like the pan already did (a latent Wayland bug too) |
| `INPUT_FROM_EVENTS_FILTER` (a `wxEventFilter`, installed by `PGM_BASE::InitPgm` for GUI programs) | records position/buttons from every mouse event; mirrors every key transition into the thread key state with `SetKeyboardState()` (so wx's `ControlDown()` and the native EDIT controls agree); synthesises `wxEVT_CHAR_HOOK` from `wxEVT_KEY_DOWN` exactly like `wxKeyboardHook` (focus window, else active window; a consumed hook consumes the key-down and wx then suppresses the `WM_CHAR`); drops a `wxEVT_LEAVE_WINDOW` while the reported pointer is still inside the window |
| `KIPLATFORM_INPUT_FROM_EVENTS_STATE` | the shared state hangs off `wxTheApp` as its client object, because kiplatform is a **static library with one copy per module** (kicommon, `_pcbnew.dll`, …): a file-static was updated by the filter in kicommon and read, stale, by the canvas in `_pcbnew` — cost two hours of "clicks land somewhere else" |
| `WX_VIEW_CONTROLS::onTimer` | skips the `IsMouseInWindow()` (real cursor) auto-pan check in this mode |
| value `cloak` | on `wxEVT_SHOW` of a top-level window: `DwmSetWindowAttribute(DWMWA_CLOAK, TRUE)` — only the owning process may cloak, so it has to be in KiCad (`libs/kiplatform/CMakeLists.txt` links `dwmapi`) |

Not patched: `DIALOG_SHIM` needed nothing once the hook is synthesised; `EDA_DRAW_PANEL_GAL::OnEvent`
/ `onEnter` focus stealing stays gated on `IsWindowActive()` (foreground) — the canvas still gets
focus on every click through `TOOL_DISPATCHER` (`SetFocus()` within KiCad's own queue works in the
background). The direct `wxGetMousePosition()` users in `properties_panel`, `lib_tree`,
`wx_aui_art_providers`, `sch_edit_frame` were routed through the seam as well.

## 3. Injector (`winstream/inject_events.py`, wrapper `run_events.py`)

Pure `PostMessageW`, no `SendInput`, `SetForegroundWindow`, `SetFocus` or `AttachThreadInput`
anywhere (grep-provable). Mouse: the deepest visible child under the point among the process's own
top-level windows in z-order (a menu or dialog above the frame wins; a disabled top-level — the frame
behind a modal dialog — gets nothing, like real input), client coordinates in `lParam`, `MK_*` button
and Ctrl/Shift bits in `wParam`, a `WM_MOUSEMOVE` before each button-down, `WM_MOUSELEAVE` to the
previous window on hand-over (the OS only does that for the real cursor), `WM_xBUTTONDBLCLK` when a
second down arrives within `GetDoubleClickTime()` (900 ms on this machine) and the double-click
rectangle (the OS synthesises that for real input only — the first drag test became a double-click
because of it). Wheel: `WM_MOUSEWHEEL` with screen coordinates to the window under the point. Keys:
`WM_KEYDOWN/UP` with scan code and extended bit to the UI thread's focus window from
`GetGUIThreadInfo` (no attaching), modifiers as ordinary `VK_SHIFT/VK_CONTROL/VK_MENU` messages, no
`WM_CHAR` (wx's `TranslateMessage` produces it). The wrapper only swaps the injector factory and lets
the tracker accept cloaked windows (`WINSTREAM_ALLOW_CLOAKED=1`); `server.py` was left alone because
spike (a) was editing it — fold this into `--inject events` afterwards.

## 4. Where the hidden window can live (capture side, measured with the winstream tracker)

| Placement | WGC frames while KiCad is driven | Notes |
|---|---|---|
| fully off-screen (`SetWindowPos` to −10000,−10000) | **initial frame only** (2 frames, then nothing for any input) | input works (verified with `PrintWindow`: Home, cursor position, selection all applied) but DWM stops composing it. `PrintWindow(PW_RENDERFULLCONTENT)` polling is the only capture: **87 ms median per 1080p frame** (≈11 fps, 8 MB readback) — not a product path |
| 2 px strip on-screen (x = 7678) | none either | "partially on-screen" is not enough when the visible strip does not change |
| on-screen, fully covered by an opaque topmost window (stand-in for VS Code) | **27.6 fps** during motion, 0 idle | the product scenario "KiCad behind VS Code"; dialogs open centred on the frame and can stick out of the covered area (Footprint Properties: 950x1265 at y 886 for a frame at y 1060) |
| on-screen, **cloaked** (`KICAD_INPUT_FROM_EVENTS=cloak`) | full rate (41/41 frames vs uncloaked on a test window; 47 frames over the edit matrix on pcbnew) | the desktop shows nothing at the window rect ([screenshot](img/win-input-patch-cloaked-desktop-vs-wgc.png)), `WindowFromPoint` returns whatever is behind, owned dialogs are cloaked too; the tracker must not skip cloaked windows. `DwmSetWindowAttribute` from another process: `E_ACCESSDENIED` |
| another virtual desktop | untested | |

Cloaked is the placement to build on: no cover window, no z-order fights, dialogs invisible as well.
Popup menus (`#32768`), combobox drop-downs and tooltips are OS windows, not wx top-levels, so they
are neither cloaked nor covered — see §6.

Real cursor / focus: the Playwright mapping probe moved the page pointer to four places and
`GetCursorPos` stayed at one point (error = full distance, i.e. the physical cursor never moved);
`GetForegroundWindow` before/after every run was the cover or another app. Two exceptions, both
attributable: (1) **launch**: a freshly started pcbnew takes the foreground once (cloaked or not) —
the product launcher must start it without activation; (2) while the sibling spike's automation
was destroying foreground windows every few seconds, the log shows two flips to my pcbnew that
coincide with a posted Esc (a `SetFocus` inside KiCad activates its frame when nobody holds the
foreground); a controlled re-run with a steady foreground app (Esc ×3, click, Home, move, 1.2 s watch
each) produced no flip.

## 7. Risks and limits

1. **Popup menus, combobox drop-downs, tooltips are OS windows** created by the menu/comctl32 code
   in KiCad's process: not wx top-levels, so neither cloaked nor covered. A context menu of a cloaked
   KiCad pops up on the user's desktop at the reported pointer (kept on-monitor by Windows). Options:
   cloak them from inside KiCad with a `WH_CBT`/`EVENT_OBJECT_SHOW` hook (untested; menus are
   fragile under per-window WGC capture, winstream §3.4), or have the helper capture the monitor
   region while a menu is open (winstream's monitor-crop) and accept the flash.
2. **Tooltips never appear** under posted input (unchanged from winstream); only a KiCad-side
   tooltip replacement would fix it.
3. **Fully off-screen windows are not composed** by DWM: capture needs on-screen (covered) or cloaked.
4. **Foreground at launch**: KiCad activates itself when the frame is shown. Launch with
   `SW_SHOWNOACTIVATE` semantics or accept one flash; in cloak mode the flash is invisible but the
   focus still leaves VS Code once.
5. **Activation-dependent behaviour** inside KiCad: `IsWindowActive()` gates the canvas focus steal
   (harmless), the Footprint Properties grid takes Esc when its editor has focus (the dialog opened in
   the foreground process behaves differently from one opened in the background). Drivers should use
   buttons for OK/Cancel where it matters.
6. **Tool-framework assumptions** that were checked: `HasCapture()`/`CaptureMouse()` in a background
   thread work for pan/zoom drags (messages are posted straight to the HWND, capture is irrelevant);
   `wxWindow::FindFocus()` follows the thread's own focus, which the dialogs and the chooser set
   correctly (`GetGUIThreadInfo` sees the chooser's EDIT control); auto-pan's `HasFocus()` check was
   not exercised; Alt combinations (`WM_SYSKEYDOWN` + `KF_ALTDOWN`) are implemented but untested.
7. **Real input while in event mode**: the WH_KEYBOARD hook still runs for hardware keys, so a key
   the hook handler skips is offered to `wxEVT_CHAR_HOOK` twice (once by wx, once by the filter). Not
   a product concern (the window is hidden) but worth a guard before upstreaming.
8. **State sharing**: the pointer state lives in `wxTheApp`'s client object because kiplatform is
   linked statically into several DLLs; anyone else using that slot would break the mode.
9. **A stale `m_infinitePanWorks`** was previously never set for the drag-zoom path; the patch sets
   it. `IsMouseInWindow()` polling in the auto-pan timer is skipped in this mode.
10. Not covered by the sweep: `wxGetMousePosition()` in the wx *library* itself (e.g. `PopupMenu`
    with a default position) — KiCad passes explicit positions in the places that matter.

## 8. What stock KiCad needs vs. the patch

Stock 10.0.x/10.99: mirror semantics only (window on the desktop, `SendInput`, focus flips, wheel zoom
moves the user's mouse). With the patch (carried in the fork, D17; upstream pitch drafted): the
editor can be cloaked and driven from VS Code alone; the helper's injector shrinks to 200 lines of
`PostMessage`. Effort to productize the input side on top of `mr/display-input`: ~1–2 days in the
helper (fold `EventInjector` into the C#/Rust helper: hit-testing, double-click synthesis, leave
hand-over, focus targeting, disabled-window rule, Alt) plus the launcher change (no-activate start,
`KICAD_INPUT_FROM_EVENTS=cloak` in the sandbox env) plus the menu/drop-down capture decision in §7.1.
The KiCad side is done for pcbnew; eeschema/symbol/footprint editors share the same code paths but
were not run. How this combines with the multi-editor surface model of [win-multi.md](win-multi.md)
(one `kicad.exe` pid, unowned sibling frames, owned dialogs; `.kicad_pcb`/`.kicad_sch` tabs + a 3D
panel) is written up in DISPLAY.md §12.6: capture-only view for everyone, the events injector against a
cloaked KiCad on builds carrying this patch, the hybrid injector as the opt-in on stock installs. A
project session in `cloak` mode is untested.

## 9. Process notes

- Sandbox: the kiwrap-seeded 10.99 root from the winstream spike (`KICAD_CONFIG_HOME` etc. via
  `bench/make_build_env.py`), scratch copy of the ecc83 demo; my pcbnew (build tree, 10.99) ran with
  `KICAD_RUN_FROM_BUILD_DIR=1`. `%APPDATA%\kicad` hash was `a90607a5…6d9d` at the start and
  `9299d260…23ee` at the end: the changed files are `8.0/eeschema.json`, `8.0/kicad_common.json`,
  `8.0/symbol_editor.json` (23:22), written by a concurrent KiCad **8.0** run of another session (the
  same event `win-multi.md` §7 reports); no 8.0 binary was started here and every process of this
  spike had the sandbox root in its environment.
- Every process this spike started was stopped by PID (pcbnew ×7 over the iterations, the server,
  the cover window, the debug listener); no `Stop-Process pcbnew` sweeps, because spike (a) had its
  own pcbnew/kicad running on the same desktop the whole time. Their `SendInput` traffic and
  foreground churn are the reason for the "shared desktop" caveats above.
- Debugging aids that stay in the code: the `KICAD_INPUT_FROM_EVENTS` trace mask (needs
  `KICAD_ENABLE_WXTRACE=1 WXTRACE=KICAD_INPUT_FROM_EVENTS`, output via `OutputDebugString`;
  `scratchpad/display2/input/dbgview.py` is a 30-line listener).
- Reproduce: build the branch, `bench/make_build_env.py --base env1099.json --build <tree> --set
  KICAD_INPUT_FROM_EVENTS=cloak`, `WINSTREAM_ALLOW_CLOAKED=1 python run_events.py --env … --pcb …
  --size 1920x1080 --pos 5740,1060 --port 8766`, then `scratchpad/display2/input/ws_drive.py` (raw
  WebSocket driver with `click/drag/chord/type/waitwin/clickwin/shotall`) or the Playwright
  `bench_a.mjs` / `drive.mjs` against port 8766.
