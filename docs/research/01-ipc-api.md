- **[high, VERIFIED LOCALLY]** Socket/token mechanics: server listens at ipc://<TempDir>\kicad\api.sock on Windows (ipc:///tmp/kicad/api.sock on Linux/mac; nng maps ipc:// to a named pipe on Windows); if a socket already exists it falls back to api-<pid>.sock. Token is a random KIID per KiCad process; a client may send an empty token and KiCad returns its token in every response (kipy adopts it); a wrong token gets AS_TOKEN_MISMATCH. KICAD_API_SOCKET / KICAD_API_TOKEN env vars are only SET BY KICAD when it launches an IPC plugin; kipy reads them if present, otherwise uses the default path. Readiness took <15 s after launch on this machine; status codes include AS_NOT_READY and AS_BUSY.

- **[high, VERIFIED LOCALLY]** Extending the IPC API is code-wise trivial but build-wise expensive. A new command = (1) a message pair in api/proto/**.proto (e.g. GetBoardLayerName is 12 lines), (2) a handler method 'HANDLER_RESULT<Resp> handleX(const HANDLER_CONTEXT<Req>&)' (~15 lines, validateDocument + work), (3) a declaration in api_handler_*.h, (4) one registerHandler<Req,Resp>() line in the ctor; new object types additionally need SERIALIZABLE::Serialize/Deserialize on the EDA_ITEM plus qa/tests/api tests; handlers are dispatched on the wx main thread and multiple handlers may claim the same message (return AS_UNHANDLED to pass). protoc runs at build time (api/CMakeLists.txt, --experimental_allow_proto3_optional, kiapi is a shared DLL because messages may only be initialized once), guarded by CMake option KICAD_IPC_API (default ON). But any such change means shipping a patched KiCad (kiapi.dll + _pcbnew.dll/_eeschema.dll), which breaks the 'upgrade KiCad underneath' requirement unless upstreamed; on this Windows box a build needs VS2022 (present: 17.9, MSVC 14.39, CMake tools) + a vcpkg clone at KiCad's pinned commit; dev-docs warn vcpkg deps take '1-10 minutes' with pre-built binaries but 'several hours' otherwise (wxWidgets, OpenCascade, ngspice, etc.). No vcpkg/VCPKG_ROOT is present here.

## Capabilities

- Live read/modify of an OPEN PCB in KiCad 9.0.x/10.0.x from any language via protobuf-over-nng (Python: kicad-python/kipy): nets, footprints (full definition incl. pads/shapes/3D models), pads, tracks, arcs, vias, zones (outline + filled polygons), shapes, text/textboxes, groups (10.0+), barcodes (10.0.1+), dimensions/reference images (10.0.1+), stackup, enabled/visible/active layers, origins, title block, netclasses, text variables, embedded files (10.0+), design variants (10.0+).
- Transactional edits: BeginCommit/EndCommit(commit|drop) grouping, CreateItems/UpdateItems/DeleteItems by KIID, undo via run_action('common.Interactive.undo'); implicit commits when no explicit commit is open.
- Placement and routing primitives: create Track/Via/Zone with net assignment; new nets are created implicitly by naming an unknown net; move/rotate/flip footprints; refill zones; 'pcbnew.InteractiveRouter.Autoroute' (Attempt Finish Selected) via run_action after AddToSelection of pads - a limited PNS-based auto-finish available in 9 and 10.
- Document management: SaveDocument, SaveCopyOfDocument (save_as), RevertDocument, SaveDocumentToString (full .kicad_pcb text without touching disk), SaveSelectionToString, GetOpenDocuments; GetKiCadBinaryPath('kicad-cli') to locate the matching kicad-cli for DRC/ERC/exports.
- Geometry helpers on the server: GetTextExtents, GetTextAsShapes, GetPadShapeAsPolygon, GetBoundingBox, HitTest, CheckPadstackPresenceOnLayers.
- GUI actions: RunAction(<TOOL_ACTION name>) reaches every pcbnew action (558 names in 10.0) - DRC dialog, import-netlist dialog, update-from-schematic, zone fill, router modes - at the cost of stability guarantees.
- Schematic (10.0): GetOpenDocuments(DOCTYPE_SCHEMATIC) only. Schematic (master/11): GetItems/selection, netlist + hierarchy queries, PlaceSymbolFromLibrary, page settings, cross-probe, variants, export jobs (SVG/PDF/netlist/BOM).
- KiCad 11 (master, not released): headless 'kicad-cli api-server --socket', OpenDocument/CreateDocument/CloseDocument (headless only), ImportNetlist (with dry_run/report), PlaceFootprintFromLibrary, library table + search commands, RunBoardJobExport{Gerbers,Drill,Position,Step/3D,PDF,SVG,IPC2581,ODB,...}, board/schematic design-rule get/set.
- Config-only enablement: KICAD_CONFIG_HOME + <ver>/kicad_common.json api.enable_server=true lets a wrapper spawn pcbnew.exe/kicad.exe with the server on, without touching the user's %APPDATA% settings.

## Limitations

- Requires a running KiCad GUI in 9 and 10 (no headless server until KiCad 11); single-threaded and synchronous - modal dialogs, active tools, routing, and zone filling return AS_BUSY; refill_zones is asynchronous so the next request may fail and must be retried.
- No schematic editing in 9/10: 10.0.0's schematic handler only answers GetOpenDocuments; HitTest/CreateItems/BeginCommit crash eeschema.exe (reproduced 4x). Standalone eeschema.exe also lacks the COMMON handler (GetVersion/Ping fail).
- No DRC/ERC execution or result retrieval through the API in 9, 10 or even master (only InjectDrcError; markers are not readable via GetItems) - must use kicad-cli pcb drc / sch erc on a saved file.
- No netlist import, no 'create board from netlist', no open/new document, no library footprint placement by LIB_ID (creates an empty footprint), no plotting/export in 9/10; ParseAndCreateItemsFromString is a stub in 10.0.
- run_action names are explicitly unstable/unsupported (kipy WARNING), differ between versions, and actions that open dialogs or start interactive tools make the editor busy or block until a human interacts.
- kicad-python 0.8.0 PyPI wheel: kipy.schematic, kipy.board_jobs, kipy.board_rules, kipy.wizards and kipy.server cannot be used (broken imports / missing proto messages); kipy.board_types.Net cannot be created directly via create_items ('Missing type mapping').
- Newer-than-KiCad client calls fail with AS_UNHANDLED (e.g. get_items_by_id on 9.0.5, get_dimensions on 10.0.0); a wrapper needs per-command minimum-version tables (from the '// Since:' comments) and must degrade gracefully.
- One fixed socket path per machine (%TEMP%\kicad\api.sock) in 9/10 - concurrent KiCad instances collide; no --socket override before 11.
- Enable flag lives in kicad_common.json (schema versions differ: 9.0 v3, 10.0 v6); KiCad may rewrite a hand-made minimal file on first run and show first-run modal dialogs (Data Collection opt-in on 9.0), so generate-then-patch is required.
- Extending the API (new .proto + handler) is small in code but requires a full KiCad source build (VS2022 + vcpkg, hours of dependency builds, tens of GB) and yields a patched KiCad that cannot be swapped for stock upgrades unless the change is upstreamed.
- Env vars KICAD_API_SOCKET/KICAD_API_TOKEN are outputs of KiCad's plugin launcher, not inputs that configure the server.

## Version notes

## Recommendations

- Adopt the IPC API as the live-editing channel for the PCB stage only, behind a version-aware adapter: probe GetVersion once, keep a per-command 'Since' table, and map unavailable commands to fallbacks (kicad-cli or file-level edits). Talk raw protobuf (vendor api/proto from each supported KiCad tag and generate _pb2 yourself) or pin kipy per KiCad major; do not rely on kipy.schematic/board_jobs/server from the 0.8.0 wheel.
- Do NOT build an in-KiCad plugin as the transport. An IPC plugin.json entry can add a 'Connect to VS Code' toolbar button (it only hands the extension the socket/token env), but all real work should go through the socket the extension opens itself. Reject the SWIG-action-plugin route (removed in 11) and the C++-handler route (needs a forked KiCad, defeats 'upgrade underneath').
- Cover the gaps with kicad-cli and files, not with the API: DRC = 'kicad-cli pcb drc' (and ERC = 'kicad-cli sch erc') on a saved copy obtained via SaveCopyOfDocument or SaveDocumentToString; schematic creation in 9/10 = generate .kicad_sch s-expressions directly, run ERC/netlist export with kicad-cli, then open the project in kicad.exe for the PCB stage; fabrication = kicad-cli pcb export gerbers/drill/pos/step; PCB-from-netlist in 9/10 = generate the .kicad_pcb with footprint definitions read from .kicad_mod files (the API will not load libraries) or drive 'common.Control.updatePcbFromSchematic'/'pcbnew.EditorControl.importNetlist' actions with the caveat that they open dialogs.
- Launch KiCad yourself with KICAD_CONFIG_HOME pointing to a wrapper-owned config dir: run once to generate <ver>/kicad_common.json, patch api.enable_server=true plus do_not_show_again flags, relaunch kicad.exe (project manager) so both editors share one server; poll Ping until AS_NOT_READY clears; treat AS_BUSY as retryable with backoff (especially after refill_zones and run_action), and never send editor messages to eeschema on 10.0.
- Design the wrapper so the KiCad 11 headless server is a drop-in: abstract 'session start' (GUI process now, 'kicad-cli api-server --socket' later), 'open/create document' (command-line file argument now, OpenDocument/CreateDocument later), and 'export' (kicad-cli now, RunBoardJobExport* later). Expect real schematic API only from 11.
- Set up a KiCad source build only as a developer diagnostic tool, not a product dependency: it is warranted to debug crashes like the eeschema 10.0.0 API crash or to contribute upstream handlers (e.g. RunDRC/marker retrieval, which do not exist even on master). Before that, use EnableAPILogging=1 in kicad_advanced (api.log) and WER minidumps with KiCad's published PDBs. The machine has VS2022 17.9 + MSVC 14.39 + CMake, but no vcpkg; budget several hours and tens of GB for vcpkg dependencies.
- Expose the tools to AI agents as an MCP/CLI layer over this adapter with explicit preconditions in each tool description (requires open board, may return busy, unstable action names), and keep DRC/ERC/exports as file-based tools so they work identically across 7-11.
- Serialize KiCad GUI usage: only one API-serving instance per machine in 9/10; the wrapper should own the lifecycle (spawn, ping, kill) and detect a foreign instance on the default socket before starting its own.
