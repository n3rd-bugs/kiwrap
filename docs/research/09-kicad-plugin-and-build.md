- **[high, VERIFIED LOCALLY]** The IPC server is OFF by default (kicad_common.json api.enable_server=false; user's own 10.0 config also has it false). It listens at ipc://<TEMP>/kicad/api.sock (macOS /tmp/kicad/api.sock); on Windows nng maps this to a named pipe named literally 'C:\Users\<u>\AppData\Local\Temp\kicad\api.sock' under \\.\pipe\ - no file ever appears on disk. - **[medium]** Windows gotcha (inferred from code): KiCad's fallback to a PID-suffixed socket ('api-<pid>.sock') only triggers when wxFileName(socket).Exists() is true, which never happens for a named pipe, so two standalone KiCad processes with the API enabled both try the same pipe name; the second silently ends up without a usable server (or worse, a squatter can pre-bind the name). A sibling task's pcbnew and mine collided on the same pipe during this session.
  - Evidence: api_server.cpp lines 115-128; the pipe name was identical for the sibling's instance and mine; Konnect issue #531 documents pipe-name squatting.

## Limitations

- No schematic authoring/reading via IPC in 9/10: only GetOpenDocuments plus stub create/update for lines/labels; no symbol placement, no GetItems, no save. Schematics on 9/10 must be produced by writing .kicad_sch S-expressions directly (as Konnect does) and validated with kicad-cli sch erc / export. The full schematic API is master/11 only.
- Known open bug #24966 (reproduced here on 10.0.0, reported through 10.0.6): the first write transaction (BeginCommit) crashes eeschema / KiCad when the Schematic Editor is open, with a null m_frame in API_HANDLER_EDITOR::checkForBusy. Any 10.x wrapper must expect eeschema to die on writes and must not run write commits while the schematic editor is open (or run pcbnew standalone).
- RunAction can start interactive tools (router, move) but they need mouse input and put the API into AS_BUSY; there is no programmatic router/autorouter API in any version (routing = wrapper-side algorithm or Freerouting DSN/SES round-trip + CreateItems of tracks/vias).
- No DRC/ERC commands in the IPC API (any version); use kicad-cli on the saved file (it operates on a private copy, so save first). No event push: selection/document-change must be polled.
- API server is disabled by default (Preferences > Plugins > Enable KiCad API); the wrapper cannot silently flip the user's kicad_common.json - it must instruct the user (or spawn its own KiCad with a private KICAD_CONFIG_HOME, which then also needs the three global library tables to avoid the setup wizard).
- Windows named-pipe semantics: the socket is not a file, discovery by file existence fails, a second standalone KiCad process cannot get its own PID-suffixed pipe (inferred from api_server.cpp), and a squatter can pre-bind the name; prefer the plugin hand-off (KICAD_API_SOCKET/TOKEN) over guessing the default path, and verify with Ping + token.
- SWIG action plugins: pcbnew only, deprecated since 9.0 and removed in 11; running a background HTTP/WebSocket server thread inside pcbnew is technically possible (GIL released, wxPython present) but board mutations from that thread bypass the undo/connectivity/refresh wrapper around Run(), need wx.CallAfter marshalling, and are a well-known source of freezes/crashes - not a viable long-term channel.
- Plugin process stdout/stderr are pipes that KiCad only drains at exit (ACTION_PROCESS::OnTerminate); a long-lived bridge process launched by KiCad must log to a file, not stdout, or it may block once the pipe buffer fills (inferred from code, not measured).
- 10.0.0 specific: GetPluginSettingsPath rejects valid identifiers ('plugin identifier is invalid'); standalone eeschema has no GetVersion/Ping handler (only pcbnew and kicad.exe register API_HANDLER_COMMON).
- Source build caveats: local MSVC 14.39 (VS 17.9) != CI's 14.44 (VS 17.14) so vcpkg binary-cache hits are unlikely without updating Visual Studio; manifest mode rebuilds dependencies after VS updates or branch switches; vcpkg must sit at a drive root; antivirus can break vcpkg builds; no official time/disk numbers exist (estimates below).
- I could not trigger the plugin toolbar button with synthetic mouse events (wxAuiToolBar ignored them), so the exec launch + env-var hand-off was verified from source and third-party plugins, not observed live; and a sibling task's concurrent GUI runs forced me to serialize experiments (shared pipe name).

## Recommendations

- Decision: do NOT set up a KiCad source build now. Build the wrapper against installed binaries and use the public symbol server for KiCad-side debugging. Concretely: kicad-cli (all versions) for ERC/DRC/exports; IPC API via kicad-python for live PCB work on 9/10 (and both editors on 11 nightly); direct .kicad_sch/.kicad_pcb S-expression generation for schematic capture on 7-10; SWIG pcbnew only as a 7/8 headless fallback. Add a KiCad 10.99 nightly install alongside 7-10 to develop the schematic/headless paths ahead of 11.
- Adopt an in-KiCad plugin, but keep it tiny and version-agnostic: one IPC 'exec' (or 'python') plugin, packaged via PCM (metadata.json runtime:'ipc', kicad_version '9.0'), with a single action scoped ['pcb','schematic'] labelled 'Connect to VS Code' that (a) reads KICAD_API_SOCKET/KICAD_API_TOKEN, (b) hands them to the VS Code extension (localhost HTTP POST or a token file in GetPluginSettingsPath/known dir), (c) optionally launches 'code' with the project, then exits. This buys reliable instance discovery on Windows (named pipe), a UI affordance in both editors, and PCM-managed installs - it does not require any KiCad source change. Do not build a SWIG action-plugin server (pcbnew-only, thread-unsafe, gone in 11).
- Make the VS Code extension the long-lived side: it owns the kipy client (single connection, timeouts, Ping+token validation, AS_BUSY/AS_NOT_READY retry), a KiCad process supervisor (detect crashes such as #24966, offer relaunch, avoid write commits while eeschema is open on 10.x, or launch pcbnew standalone with a private KICAD_CONFIG_HOME containing kicad_common.json + the three global lib tables), and the per-version capability matrix. Expose everything to agents through MCP (stdio + streamable HTTP) so Claude Code/Copilot/Cursor can drive it.
- When a KiCad-side bug blocks you, first reproduce with EnableAPILogging=1 (logs/api.log) and analyse minidumps with cdb/WinDbg or Visual Studio using srv*<cache>*https://symbols.kicad.org/kicad-stable (0.5 h setup, demonstrated here); check out the matching tag for source view. Only escalate to a source build when you need to change KiCad code or step with unoptimised locals.
- A source build IS genuinely required for: contributing schematic-API handlers/protos upstream (targets master/11, must follow proto compatibility rules and add qa/test/api tests), adding a headless/ERC/DRC API command, or shipping a patched KiCad. It is NOT required for: driving installed binaries, writing IPC/PCM plugins, diagnosing crashes, or regenerating kipy protos (kicad-python repo carries them). If/when you do build: update VS 2022 to the current 17.14.x first (to match CI's MSVC 14.44 and hit the NuGet binary cache), clone vcpkg to a drive root at build.ps1's $vcpkgCommit, add the kicad-gitlab NuGet source, install swigwin 4.3.1, use the msvc-win64-debug preset, and run from VS with launch.vs.json. Effort estimate on this machine (no official numbers): environment setup 1-2 h; dependencies 10 min-1 h with cache hits, else 2-5 h wall (OCCT, wxWidgets, ICU, Python, protobuf, both Debug+Release for x64-windows); KiCad itself ~30-60 min for a Debug/RelWithDebInfo build with 24 threads, minutes incremental; disk 40-80 GB (vcpkg ~30-50 GB + build tree 10-25 GB). Budget roughly one working day for the first successful debug build, then it is cheap to keep.
- Wrapper hardening derived from the experiments: treat every IPC call as fallible (AS_BUSY when an interactive tool is active, AS_NOT_READY during startup/shutdown, connection drops on crash); never call RunAction for interactive tools; save before invoking kicad-cli DRC/ERC; log plugin processes to files not stdout; validate identifiers as reverse-DNS with >=3 labels; and never modify the user's %APPDATA%/kicad settings - instruct the user to enable the API or spawn a sandboxed KiCad.
